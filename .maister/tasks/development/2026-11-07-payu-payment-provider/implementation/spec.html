TL;DR

Finish the PayU REST v2.1 provider drafted in commit 2259c9313. The attendee is redirected to the PayU hosted page and comes back to a new return callback. Signed notifications and a force-check confirm the payment.

PayUManager gets a money-safe order lifecycle. A new order is created only after the previous one is confirmed CANCELED or not found, or is confirmed deleted. Once a payable order may exist, the manager never returns failed. It also gets a tri-state order read, a shared cancel routine (DELETE) and validityTime, plus the M4–M8 hardening. All 6 red-gate tests turn green.

New: PayUPaymentWebhookController, PayUCallbackController, the public payu-payment-proxy, admin labels and panels, EN i18n, an optional customerIp on PaymentSpecification, a currency hook in BaseE2ETest, and unit, WireMock integration and sandbox e2e tests. There is no Flyway migration and no change to TicketReservationManager.

The work ships on feature/payu, fix/pl-translations, fix/stepper-active-color and plo-pl, all pushed, with no upstream PRs and no AI trailers.

Key Decisions

  • Re-confirm with an existing PENDING transaction, matrix below:
    • COMPLETED and validated → transaction COMPLETE (shared routine), then success.
    • PENDING → pending. WAITING_FOR_CONFIRMATION → capture, then pending.
    • NEW → shared cancel; a new order only when the cancel is confirmed, otherwise pending.
    • A confirmed CANCELED or NOT_FOUND → create a new order.
    • A read ERROR or a COMPLETED mismatch → pending, keeping the transaction.
    • Rule: never return failed once a remote order may still be payable. The status read has no side effects. The COMPLETED branch updates the transaction and the WAITING branch captures.
  • The order read is tri-state: retrieveOrder returns FOUND, NOT_FOUND or ERROR (timeout, I/O, 5xx, 401 after the retry, bad body).
  • Cancelling is one shared routine used by the NEW row and by discardTransaction. It counts as cancelled only when the body has status.statusCode == SUCCESS (whatever the HTTP code), or when a re-read shows CANCELED. (Superseded by post-implementation amendment PI1/PI2: after the DELETE the order is always re-read, and only a CANCELED or NOT_FOUND re-read counts as cancelled.)
  • A NEW order, by context: NOT_RELEVANT in webhooks; error in forceTransactionCheck, which core treats as "no action" and turns into pending.
    • Why: the stuck check marks a reservation STUCK when it gets NOT_RELEVANT, and the red gate forbids TRANSACTION_INITIATED for NEW.
    • ERROR is the only non-state-changing result that satisfies both.
  • After a valid signature, a payload is always returned. Refunds, unknown shapes and extOrderId mismatches give NOT_RELEVANT (200). Only an invalid signature or unparseable JSON gives 500. That is intentional: PayU retries, so a wrong second key that an admin later fixes is self-healing.
  • Webhook for an unknown reservation → 200 + WARN. Only an empty body → 400.
  • Return callback:
    • With error: cancel, then overview + toast. The toast also shows when the cancel fails but no pending transaction is left.
    • Without error: force-check. A failure goes to the overview + toast, and anything else to /book.
    • A NEW order with no error counts as in progress. It ends when PayU auto-cancels at validityTime.
  • Showing the cancellation: query parameter paymentCancelled=true shows the toast with the new EN key reservation-page.payment.cancelled (one key beyond FR12).
  • Refund idempotency: extRefundId = <rid>-refund-<amountCents>-<k+1> (k from GET refunds). A timeout or I/O failure triggers a re-read, and a refund carrying that id counts as success. (Scope clarified by PI5: this protects a same-call retry and concurrent duplicates, not an operator retry after a refund that landed.)
  • customerIp: a nullable field plus a withCustomerIp wither. Every existing constructor keeps its signature. IP = first XFF entry, else remoteAddr, else 127.0.0.1.
  • Endpoint override for tests: alfio.payu.endpoint-override via a second @Autowired constructor. The public 5-arg constructor stays, and a WARN is logged when the override is set. (PI7: ignored in live mode.)
  • Currency gating (I3) in isActive when a purchase context is present.
  • Labels: "PayU: BLIK, fast transfer, card" (EN) and "PayU: BLIK, szybki przelew, karta" (PL). The new admin shows the raw PAYU with the credit-card icon.
  • Secrets stay plain TEXT (I6). Gson stays for PayU JSON.

Open Questions / Risks

  • warningThe public sandbox POS 300746 is shared. Its page markup must be verified live, and it probably accepts only PLN (hence the e2e currency hook).
  • warningDELETE on a PENDING order is unverified. (Resolved on the sandbox, see PI4: DELETE on PENDING → CANCELED, no funds after.) If PayU refuses it, the order counts as not cancelled: discard returns false and re-confirm returns pending. If funds can still arrive, restrict the DELETE to NEW.
  • warningA NEW order past the reservation validity gives ERROR in the stuck check (no STUCK). The reservation is held until PayU auto-cancels; if PayU never does, tickets are held with only a WARN log.
  • warningWAITING_EXTERNAL_CONFIRMATION gap (inherited core behaviour): no scheduler selects it. A lost final notification holds tickets until a force-check runs.
  • infoWAITING_FOR_CONFIRMATION in the stuck check: captured and reported as pending (not stuck). It completes on the next run.
  • warningA COMPLETED mismatch gives ERROR in webhooks and pending in doPayment, so PayU retries. Money can sit captured until a manual refund.
  • infoPOST /orders timeout after PayU created the order: failed. The order is unreachable by the buyer and auto-cancelled at validityTime.
  • infoLock duration: up to about 5 calls × 10 s under the reservation row lock (worst case about 50 s). A reverse-proxy timeout above 60 s is recommended. (Superseded by PI6: the bound also includes the cancel polling budget; recommend a reverse-proxy read timeout ≥ 120 s.)
  • infoNo connect timeout on the shared HttpClient.
  • infoXFF can be spoofed, and remoteAddr can be IPv6: check that PayU accepts IPv6.
  • infoThe descriptor must be regenerated on feature/payu and on plo-pl. The new branches do not exist yet, and the backup ref is local only.

Goal & scope

Make PayU a production-ready alf.io payment proxy. It must be configurable at system or organization level, offered to attendees as "PayU: BLIK, fast transfer, card", and confirmed reliably by return + force-check and by signed notifications. It must never double-charge, leave payable orphan orders, or cause endless notification retries.

User stories

Attendee
I want to pick PayU on the overview, pay with BLIK, a fast transfer or a card on PayU's page, and land on my confirmation. This lets me buy a ticket with the methods common in Poland.
Attendee who cancels on PayU
I want to come back to the overview with a clear message and pick a method again, so that I am not stuck on a "payment in progress" page.
Attendee who presses "Pay" twice
I want the second attempt not to create a second payable order, so that I am never charged twice.
Organization / system admin
I want a PayU panel in the payment settings, so that I can configure PayU without touching the database.
Reservation operator
I want PayU reservations labelled with a card icon, and I want to refund them in full or in part (also when I retry after a timeout), so that I can handle cancellations.

PayUManager details (constructors, config access, read, cancel, completion, parsing, discard, cache, timeouts, refunds)
  • Constructors: the public 5-arg one stays; a second @Autowired one takes alfio.payu.endpoint-override.
  • Config access: everything comes from the ALL_KEYS map via getFor(Set, level). Never the single-key overload, which the red-gate mock does not stub.
  • Constants: RETURN_URL_TEMPLATE = …/payment/payu/return, plus ADDITIONAL_INFO_RESERVATION_ID, the currencies and the buyer-language set (to be verified).
  • retrieveOrder, three outcomes:
    • FOUND: HTTP success, SUCCESS body, non-empty orders.
    • NOT_FOUND: HTTP 404 or PayU "not found" (DATA_NOT_FOUND, to be verified).
    • ERROR: everything else.
  • cancelOrder: DELETE. CANCELLED when the body has SUCCESS (any HTTP code), or when a re-read shows CANCELED or NOT_FOUND. (Superseded by PI1/PI2.) After the DELETE (any response) the order is always re-read; CANCELLED only when the re-read is CANCELED or NOT_FOUND; a COMPLETED re-read → ERROR log, NOT_CANCELLED. Otherwise NOT_CANCELLED (WARN).
  • completeTransaction: validate amount, currency and extOrderId, then transaction COMPLETE + PayUToken. A mismatch is logged at ERROR and changes nothing.
  • doPayment:
    • extOrderId = <rid>-<8 random hex chars>.
    • validityTime = max(remaining seconds, 300), falling back to RESERVATION_TIMEOUT when the reservation is null.
    • Reservation validity = now + validityTime + 5 min. Clock-based throughout.
    • failed only when no previous order may be payable.
  • parseTransactionPayload: an invalid signature or JSON gives empty. Otherwise an ORDER, REFUND or UNRECOGNIZED payload (null-safe). processWebhook: a non-ORDER kind or a different orderId gives notRelevant. forceTransactionCheck never touches reservation.
  • discardTransaction:
    • NEW/PENDING → cancelOrder; true only if CANCELLED.
    • CANCELED / NOT_FOUND → true.
    • COMPLETED / WAITING / ERROR → false.
  • initTransaction → errorToken(msg, true), a private static nested TransactionInitializationToken. Core then reconciles via the force-check.
  • Token cache: Caffeine, keyed by endpoint + clientId + SHA-256 of the secret. Renewed 60 s early. A missing expires_in means 300 s. A 401 invalidates the key and retries once.
  • Timeouts: 10 s per request, including OAuth.
  • Refund:
    • A GET of the refunds gives k; extRefundId = <rid>-refund-<amountCents>-<k+1>.
    • A timeout or I/O error triggers a re-read; the id found counts as true.
    • If the initial GET fails, return false and send no POST.
  • getInfo: refunded = sum of FINALIZED refunds.
  • Code rules: no ternaries (do not copy the one in PaymentManagerUtils), allowed Lombok only, GPL headers, no Jackson 2.
customerIp, frontend, admin, i18n, stepper, Docker

Post-implementation amendments

Recorded after implementation and the sandbox runs (CP-W1, spec drift). Where an earlier statement in this spec disagrees, these rows win.

IDChange
PI1cancelOrder: after the DELETE (any response: SUCCESS, non-SUCCESS, timeout or I/O error) the order is always re-read. CANCELLED only when the re-read is FOUND+CANCELED or NOT_FOUND. A COMPLETED re-read → ERROR log, NOT_CANCELLED. Reason: on the sandbox, DELETE on a COMPLETED order returns SUCCESS but the order stays COMPLETED, so a SUCCESS body alone proves nothing. Commit dcedbd9ad.
PI2PayU applies an accepted DELETE asynchronously (the order can still be NEW or PENDING right after it). After an accepted DELETE the order is re-read with bounded polling (commit 6475c6ecb), now with an overall time budget and an injectable pause (verification fix batch), so the time spent polling under the reservation lock is bounded.
PI3IPv6 customerIp is normalized before it is sent: brackets and the zone index (%eth0) are stripped, because PayU rejects them. Commit 81ae831b2.
PI4Sandbox facts: DATA_NOT_FOUND comes with HTTP 404. DELETE on a PENDING order → CANCELED, and no funds arrive after it (the M5 "restrict to NEW" fallback is not needed). A localhost notifyUrl is accepted at order creation. The refunds listing has the shape {refunds:[{refundId, extRefundId, amount, currencyCode, status PENDING|FINALIZED|…}]}.
PI5Refund idempotency wording: the deterministic extRefundId protects a same-call retry after a timeout (the re-read finds it) and concurrent duplicates.
